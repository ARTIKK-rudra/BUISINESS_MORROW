# ML Evaluation Report

**Report date:** 2026-09-28  
**Status:** Research prototype; no production business dataset was present in the repository.

## Demand forecasting

The demand pipeline was executed against a reproducible **synthetic fixture** generated by
`backend/app/ml/synthetic_evaluation.py`. It contains 365 daily observations from a seeded Poisson
process with weekday and annual seasonality plus a small trend. The final 67 days were held out in
time order. Predictions were one-step rolling forecasts, using observations available before each
forecast date. Metrics are demand units per day except percentages.

| Model | MAE | RMSE | sMAPE | MAPE on nonzero actuals |
|---|---:|---:|---:|---:|
| Naive: last observation | 5.433 | 6.350 | 25.102% | 26.323% |
| Seasonal naive: same weekday last week | 4.478 | 5.436 | 20.765% | 21.051% |
| Random forest with lag/calendar features | 3.964 | 4.971 | 18.669% | 18.122% |

The random forest was selected on this fixture by holdout sMAPE. These results measure only this
synthetic fixture; **they are not measured business accuracy and must not be presented as a real
business performance claim**. No real production sales history was available for evaluation here.

The current feature set uses lag 1/7/14, rolling 7/28-day mean and 7-day deviation, and cyclical
weekday/month features. It does not yet use prices, promotions, holidays, or category features:
future campaign/holiday plans are not modeled, and per-product training makes a static category
feature non-informative. Recorded sales can understate demand during stock-outs; there is not yet a
reliable daily availability history to censor or correct those targets.

## Stock-out risk

The application combines current on-hand stock, product forecasts (or ingredient demand derived
from recipes), supplier lead time, and forecast interval widths. Lead-time demand intervals are
aggregated using a normal approximation that assumes independent daily forecast errors. The
probability is explicitly **uncalibrated**. It is persisted with its assumptions and factors; it
must not be described as validated probability until historical stock-out outcomes are available
for temporal calibration and backtesting.

The shared normal-approximation function was also exercised on 1,000 explicitly synthetic
independent-Poisson scenarios with known mean demand and supplier lead times: Brier score **0.0598**
versus **0.2328** for a constant base-rate predictor (Brier skill **0.7433**). This is a
distributional smoke check where the simulation assumptions match the calculation. It excludes
forecast estimation error, correlated demand, expiry, and uncertain supplier lead times, and is not
operational calibration evidence.

## Anomaly detection

Isolation Forest is fitted separately on available sales, refunds, inventory movement history
(per inventory item), and supplier price history (per supplier item). Each run requires at least 20
records in a group. Outputs are review signals with contributing robust deviations; they are not
proof of errors or fraud. There are no labeled anomaly outcomes in the repository, so precision,
recall, false-positive rate, and accuracy are **not available**. Small groups are reported as
skipped rather than assigned fabricated results.

The same Isolation Forest/RobustScaler method was run on a labeled synthetic fixture: 1,000 normal
training rows and 550 held-out rows, including 50 injected extreme sale/discount patterns. With
`contamination="auto"`, precision was **0.2252**, recall **1.0000**, and F1 **0.3676**. This high
false-positive rate shows that the default detector needs careful review and threshold validation;
these fixture metrics do not describe real anomaly performance. Runtime alerts remain review
signals, not confirmed anomalies.

## Model registry and data

Demand training uses real tenant-scoped completed sales records and records temporal holdout
metrics, dataset kind, feature names, selected version, artifact URI, training timestamps, and
provenance. A reproducible command is:

```bash
cd backend
python -m app.ml.train_demand --business-id <business-uuid> --product-id <product-uuid>
```

Forecasts and stock-out predictions are persisted with model version, timestamp, factors, and
uncertainty. Model artifacts use `ML_ARTIFACT_DIR` (a persistent Docker volume in local Compose).
Artifacts contain executable Python serialization and must only be loaded from the trusted
application artifact store.

## Relational-model decision

A GNN was **not implemented**. Although entity tables and recipe/supplier links exist, this
repository has no populated multi-business relational history, graph-level labels, or evaluation
design demonstrating lift over the time-series and tabular baselines. Implementing a graph model
now would be speculative. Reconsider only after sufficient historical product/ingredient/supplier
and order/customer relationships exist, and compare against non-graph baselines with a temporal or
entity-held-out evaluation.
